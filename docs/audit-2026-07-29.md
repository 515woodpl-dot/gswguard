Two findings were escalated by live verification:

- **C2 was worse than first reported.** Supabase's default grants give `anon` and
  `authenticated` full DML on all 23 public tables, so RLS was the *only*
  control, not defence in depth. Migration 0012 revokes the grants as well as
  dropping the policies.
- **C3 concealed a remediation hazard.** `RemediationGuard.should_submit` tested
  `not evidence.passed`, which is true for missing evidence too. A policy with
  `automatic_remediation` enabled would have submitted a privileged remediation
  job against a device that had merely failed to report the field. Now only a
  measured `failed` qualifies.

Still open, in priority order: implement the Windows security collectors (task
#10 — until then policies are honestly reported as unscoreable), validate the
agent changes on Windows CI (task #9), then H5 (blocking DB I/O / no pooling),
M1 (single rate-limit bucket), M2 (offline threshold equals heartbeat interval),
M3 (inventory history deleted on every submission), and M11 (the deployed Pi
tree is not a git repository).

## Scope and method

This audit reviews the tree at `/opt/gswguard` on the Raspberry Pi against the
master specification, the baseline and phase threat models, the ADRs, and the
`verification-status.md` gate map. Unlike the 2026-07-28 audit, findings here
were checked against the **running deployment** and against the **published
v0.1.1 release artifacts**, not only the source.

Direct verification performed:

- `docker compose ps` and `ss -tlnp` on the Pi.
- Unauthenticated HTTP probe of the API over the LAN interface.
- `printenv` inside both running containers (variable names and non-secret
  values only).
- Download of the v0.1.1 release assets and cryptographic verification of the
  signed manifest against the pinned public key.
- Static reading of every API module, the dashboard client, the Windows agent,
  the PowerShell install/update/verify scripts, all 11 migrations, and all
  three CI workflows.
- Enumeration of HTTP endpoints actually exercised by the test suite.

## What is genuinely solid

State this first, because it is real and it closes most of the standing gate.

**The signed update chain works.** Downloading
`releases/download/v0.1.1/{yorguard-windows-agent.zip,manifest.txt,manifest.sig}`
and verifying independently:

- The manifest's RSA PKCS#1 v1.5 / SHA-256 signature **validates** against the
  2048-bit public key pinned in `scripts/YorGuardIntegrity.ps1`.
- The package SHA-256 (`437b486a…55cc93`) **matches** the signed manifest.
- All four release assets are present and reachable.

Against the six required corrections in `verification-status.md`:

| Item | Status |
| --- | --- |
| 1. Trusted first-install verifier, never downloaded unverified | Closed — the bootstrap verifies the manifest with an embedded pinned key, then runs the installer only from the hash-verified package |
| 2. Preserve `appsettings.json`; remove consumed enrollment token | Closed — `update-windows-agent.ps1` excludes it; `EnrollmentTokenStore.Clear()` removes the token |
| 3. Verifier compatible with the scheduled task's runtime | Closed — the task runs `powershell.exe` (5.1), where `RSACryptoServiceProvider`/`FromXmlString` is supported |
| 4. Bind to one immutable signed release | Closed — but it removed the only upgrade channel; see H2 |
| 5. Decide/test the HTTPS transport rollout | Closed in the clients; undermined by the container port binding; see C1 |
| 6. Keypair, CI secret, pinned key, signed release, one Windows end-to-end test | Signing side closed and verified; the Windows end-to-end install/update test has not happened, and the update leg cannot currently pass |

Other genuinely sound work: hash-chained audit appends serialized by
`pg_advisory_xact_lock` to prevent chain forks; job claiming via
`FOR UPDATE SKIP LOCKED` with leases, attempt caps and expired-lease reclaim;
transactional single-use enrollment-token consumption under `FOR UPDATE`;
membership-infrastructure failure returning 503 rather than silently
downgrading authorization; DPAPI plus explicit protected ACLs for the device
credential; downgrade protection in the updater; typed action payloads with
`extra="forbid"`; RLS enabled on every tenant-owned table; `/docs` correctly
disabled in production.

## Critical — fix before any Windows endpoint rollout

### C1. The Tailscale-only boundary is not enforced; the API is on the LAN in plaintext

`docker-compose.yml` publishes `"8000:8000"` and `"3000:3000"`, which bind
`0.0.0.0` (and `::`). Verified live on the Pi:

```text
0.0.0.0:8000->8000/tcp, :::8000->8000/tcp
0.0.0.0:3000->3000/tcp, :::3000->3000/tcp
```

```text
$ curl http://10.1.10.246:8000/api/v1/health/ready        -> 200
$ curl -X POST http://10.1.10.246:8000/api/v1/devices/enroll  -> 401 invalid_or_expired_token
```

Every host on the local network can reach enrollment, heartbeat, and inventory
over unencrypted HTTP. Device credentials and enrollment tokens ride that
transport. `docs/operations/tailscale-private-https.md` documents Serve
proxying to `127.0.0.1:3000` / `127.0.0.1:8000`, which is what the compose file
should bind. This contradicts trust boundary 3 and the agent/receiver's own
HTTPS enforcement.

Fix: `127.0.0.1:8000:8000` and `127.0.0.1:3000:3000`.

### C2. RLS lets an administrator bypass every API action control

- `devices_admin_mutate` (0002) is `for all` — SELECT, INSERT, UPDATE, DELETE.
- `jobs_admin_create` (0005) is `for insert` with a check on organization only.
- `jobs_admin_cancel` (0005) is `for update using (...)` with **no** `with check`.

The Supabase anon key is public by design and the dashboard holds a user JWT.
An administrator session — or a stolen one — can therefore go straight to
Postgres and:

- insert a job with any `action_type` and any `action_payload`, with
  `confirmation_at` set and no `reason`, bypassing `JobRequest.validate_command`
  and `validate_payload` entirely;
- rewrite a pending `refresh_inventory` job into `install_software` or
  `restart` after creation;
- overwrite `devices.credential_hash` with the hash of a credential they chose,
  minting a working device credential with no enrollment token;
- delete device rows.

None of these paths writes an audit row. This contradicts SECURITY.md
("Sensitive actions are typed, confirmed, audited, bounded, and expiring";
"The agent never accepts arbitrary … payloads") and the baseline threat model's
administrator-compromise control.

Fix: client roles get SELECT only on `devices` and `jobs`; all mutation goes
through the API, which already validates and audits.

### C3. Compliance checks data the agents never collect

`WindowsInventoryCollector.cs:56-64` hardcodes every security field:

```csharp
["bitlocker"] = "not_collected",
["firewall"] = "not_collected",
["defender"] = "not_collected",
["secure_boot"] = "not_collected",
["tpm"] = "not_collected",
["automatic_updates"] = "not_collected",
```

`scripts/yorguard-receiver.py:122-129` does the same for macOS
(`not_collected` / `not_applicable`). `FieldRule.evaluate`
(`compliance.py:79-89`) compares case-folded equality against the expected
value, and the dashboard only offers `on`/`off`, `healthy`, `present`,
`Pro`/`Enterprise`/`Education`.

Therefore **every policy fails on every device and every compliance score is
0%**, and the device rows and detail modal will display it. The Policies view
shipped on 2026-07-29 sits entirely on top of this. Either implement the
Windows collectors (`Get-BitLockerVolume`, `Get-MpComputerStatus`,
`Confirm-SecureBootUEFI`, `Get-Tpm`, firewall profile, WU policy) or gate the
Policies view behind a "no evidence collected yet" state.

Related: `windows.update_status` is also `"not_collected"`, and
`local_accounts[].is_administrator` is hardcoded `false` on both platforms, so
inventory reports a value the spec asks for and the agent does not measure.

### C4. The authorization boundary has no automated tests

The 40 passing API tests reach exactly three HTTP endpoints: `/health/live`,
`/api/v1/health/ready`, `/api/v1/auth/me`. Everything else is a unit test
against an in-memory fake.

Untested at the HTTP layer: organization scoping on `/api/v1/devices`,
`/inventory/latest`, `/jobs`, `/compliance/policies`, `/compliance/latest`;
the owner/administrator role gates on `/enrollment-tokens`, `/jobs`,
`/compliance/policies`; device-credential authentication on `/devices/enroll`,
`/devices/heartbeat`, `/devices/inventory`, `/device/jobs/claim`,
`/device/jobs/{id}/complete`, `/device/jobs/{id}/fail`.

The baseline threat model requires negative cross-tenant tests covering "both
direct table access and API paths". Neither exists: the pgTAP suites in
`supabase/tests/` have still never been executed.

Also, `test_auth.py` and `test_membership.py` mutate `app.state.jwt_verifier`
and `app.state.membership_repository` globals, so the suite is order-dependent.

## High

### H1. The Windows agent stops reporting permanently after one exception

`Worker.cs:28` loads the credential **once, outside the loop**.
`Worker.cs:71`, in the generic `catch (Exception)`, sets `credential = null`.
Because the enrollment token was already deleted after first enrollment, the
next iteration falls into the `string.IsNullOrWhiteSpace(agentOptions.EnrollmentToken)`
branch and logs "No device credential or enrollment token is configured;
retrying later" every five minutes — forever. The credential is never re-read
from disk.

Separately, `credentialStore.Load()` on line 28 is outside the `try`. A
`CryptographicException` from `ProtectedData.Unprotect` (DPAPI machine-key
change, image restore) propagates out of `ExecuteAsync` and, with the default
`BackgroundServiceExceptionBehavior.StopHost`, stops the service.

A 401 from a revoked credential surfaces as `HttpRequestException` and is
retried on the same backoff indefinitely, with no distinct handling or alert.

### H2. The self-update path cannot ever fire

`install-windows-agent.ps1:119` creates the scheduled task with
`-PackageUrl`/`-VersionUrl` pinned to the release being installed
(`…/download/v0.1.1/…`, defaults at lines 21-24).
`update-windows-agent.ps1:49-51` fetches that pinned `version.txt`, compares it
to the installed `version.txt`, and `exit 0` when equal — which it always is.

Closing gate item 4 (pin to an immutable ref rather than `releases/latest`)
removed the only upgrade channel without adding a replacement. There is now no
update path except manually re-running the bootstrap on each machine. A signed
"current version" pointer, fetched separately from the pinned package URL, is
needed.

### H3. The enrollment token is left readable by every local user

`install-windows-agent.ps1:98-111` writes the one-time token in plaintext to
`$env:ProgramFiles\YorGuard\Agent\appsettings.json` and applies **no ACL
hardening** to the install directory or that file. The default Program Files
ACL grants `Users: Read`. Any standard user can read the token — and the API
URL — during the window between install and first successful enrollment, and
can race the service to enroll a rogue device with it.

`DeviceCredentialStore.RestrictToServiceAccounts` does this correctly for
`C:\ProgramData\YorGuard`. The install directory needs the same treatment.

### H4. High-privilege secrets are provisioned to the dashboard container

`docker-compose.yml` gives both services `env_file: .env.local`. Verified in
the running dashboard container:

```text
DATABASE_URL  SUPABASE_JWT_SECRET  SUPABASE_SERVICE_ROLE_KEY
```

None of the three is read by any dashboard code — `app/api/runtime-config/route.ts`
returns only `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `API_BASE_URL`,
`AGENT_RELEASE_REF`, `AGENT_SIGNING_PUBLIC_KEY_XML_BASE64`. Any SSRF or RCE in
the Next.js server yields the service-role key and the JWT signing secret.
`SUPABASE_SERVICE_ROLE_KEY` is also present in the API container and read by
nothing there either.

This contradicts trust boundary 2 and the threat model's statement that
service-role credentials "remain backend/deployment secrets".

### H5. Blocking database I/O inside async handlers on a single worker

Every repository method opens a **new** synchronous psycopg connection inside
an `async def` FastAPI handler — `membership.py:30`, `devices.py:57/75/131/149`,
`jobs.py:173/235/248/304`, `inventory.py:154/203`, `compliance.py:180/198/242`,
and `main.py:93` in `/health/ready` itself.

Consequences on the single-process uvicorn container: one slow query stalls
every concurrent request, including readiness; each authenticated request costs
at least two new connections (membership resolve plus the handler's own);
`/api/v1/compliance/latest` opens two and re-evaluates all policies for all
devices from scratch on every call; there is no pooling anywhere, against a
Supabase connection cap.

### H6. Devices and Supabase users can no longer be deleted

`audit_log.actor_user_id` (0001) and `audit_log.actor_device_id` (0011) are both
`on delete set null`. `audit_log_immutable` (0001) is a `before update or delete`
trigger that raises unconditionally. The FK's SET NULL action issues an UPDATE
against `audit_log`, which fires the trigger and raises
`audit_log is append-only`.

So once a device or an auth user has any audit history, deleting it fails. The
trigger is right; the FK action is wrong — these actor columns should be plain
`uuid` without a cascading FK, or `on delete no action`.

## Medium

**M1. Rate limiting collapses to one bucket behind Tailscale.**
`TRUSTED_PROXY_HOPS` is unset (verified — defaults to 0), so
`RateLimitMiddleware._client_key` returns `request.client.host`. Tailscale Serve
proxies from `127.0.0.1`, so the whole tailnet — every endpoint agent and every
dashboard session — shares a single 120 req/min bucket. The dashboard issues
five API calls per load. This is a self-DoS risk and provides no per-client
isolation. Enrollment is not limited more tightly than health checks, contrary
to the threat model's "Enrollment endpoints are rate-limited".

**M2. Devices flap to "offline" every cycle.** `devices.py:153` marks a device
offline when `last_heartbeat_at < now() - interval '5 minutes'`, and both agents
heartbeat at exactly 5-minute intervals. Any latency puts devices into "Needs
attention". Also, `heartbeat()` (line 140) stores the **device-supplied**
`observed_at` as `last_heartbeat_at` rather than the server's `accepted_at`, so
a device may report up to 5 minutes into the future.

**M3. Inventory history is destroyed on every submission.**
`inventory.py:168-171` deletes all snapshots for the device before inserting.
Downstream effects: the `unique (device_id, payload_hash)` dedupe is unreachable
and the returned `deduplicated` flag is dead (`row is None` is never true);
`software_changes()` can never see a previous snapshot; `software_inventory` and
`software_change_events` are never written, so Phase 5 change notifications
cannot fire in production regardless of the scheduler.

**M4. `validate_archive_member`'s ambiguity check is dead code.**
`packages.py:75` reads
`if path.is_absolute() or ".." in path.parts or ":" in path.parts[0] if path.parts else False:`
which Python parses as `(A or B or C) if path.parts else False`. Verified
behaviour: `''`, `'.'`, `'./x'`, `'a/./b'` are all **accepted**, because
`PurePosixPath` normalizes `.` away so `parts` never contains `''` or `'.'`.
Traversal, absolute and drive-letter cases are still correctly rejected. Impact
is low; the check is non-functional as written.

**M5. Package bytes are delivered before verification.**
`PackageDownloadService.stream` yields every chunk and only then checks total
size and SHA-256. A tampered package reaches the consumer in full before the
mismatch is raised, so the agent must be assumed to re-verify independently.

**M6. Approved-folder path validation misses documented Windows cases.**
`file_ops.py:38` rejects `""`, `.`, `..`, `:` and NUL, but not reserved device
names (`CON`, `NUL`, `PRN`, `AUX`, `COM1`–`LPT9`), trailing dots/spaces, or
Unicode/case-normalization variants — all explicitly required by
`docs/security/approved-folder-file-operations-threat-model.md`. The
`.quarantine` directory sits inside the root and is reachable as an ordinary
upload path.

**M7. CI gaps.** `ci.yml:41` uses `npm install`, not `npm ci`, so the dashboard
lockfile is not enforced (the threat model requires pinned dependencies).
`eslint` exists in `apps/dashboard/package.json` but appears in no CI job and
not in `npm run validate` — the 2026-07-29 "Dashboard lint: passed" was a manual
run that can silently regress. `security.yml:37` sets `continue-on-error` on the
C# CodeQL leg, so C# findings never block a merge. No `npm audit` or
`pip-audit`; `dependency-review` runs on pull requests only. `pip install` has
no hash pinning, and `pytest` ships inside the production API image.

**M8. `.env.example` has drifted from the running system.** It documents four
variables no code reads (`SUPABASE_SERVICE_ROLE_KEY`, `RESEND_API_KEY`,
`GOOGLE_DRIVE_SHARED_DRIVE_ID`, `BOOTSTRAP_EMAIL`) and omits five the
deployment depends on (`API_BASE_URL`, `AGENT_RELEASE_REF`,
`AGENT_SIGNING_PUBLIC_KEY_XML_BASE64`, `SUPABASE_JWT_JWKS_URL`,
`SERVICE_VERSION`). An operator cannot configure a new instance from it.

**M9. No service recovery, and native exit codes are ignored.**
`install-windows-agent.ps1:116-119` pipes `sc.exe` and `schtasks.exe` output to
`Out-Null`; `$ErrorActionPreference = "Stop"` does not apply to native exit
codes, so a failed `sc create` is silent until `Start-Service` throws. No
`sc.exe failure` recovery actions are configured, which the baseline threat
model requires under "Service tampering/uninstall".

**M10. Updates have no rollback.** If a new binary fails to start,
`update-windows-agent.ps1:91` throws and leaves the endpoint with the service
stopped and no automatic revert to the previous version.

**M11. The deployed Pi tree is not a git repository.** `git rev-parse` fails in
`/opt/gswguard`. The running source is an unversioned copy, so there is no way
to confirm it matches reviewed commit `e3e35b4`, to diff it, or to roll it back.
The 2026-07-29 report's "Git diff check: passed" and its Pi-deployment note
cannot refer to this host.

## Low

- `AgentOptions.ApiBaseUrl` is not validated for `https://` in the agent itself
  (only in the installer and the macOS receiver).
- `WindowsInventoryCollector.Query` never disposes the `ManagementObject`s it
  returns — COM handles leak on every 5-minute cycle.
- Windows software inventory reads `HKCU\…\Uninstall` while running as
  LocalSystem, i.e. the service account's own profile, not the logged-in user's.
- The macOS receiver's 2000-app cap `break`s only the inner loop, so scanning
  `~/Applications` can exceed the API's `max_length=2000` and 422 the entire
  submission.
- `SoftwareScanScheduler.next_due` re-rolls jitter on every call, so `due()`
  returns inconsistent answers for the same `last_scan`.
- `auth-panel.tsx` calls `createClient()` on three separate paths (151, 337,
  355) instead of memoizing one client; the `onAuthStateChange` unsubscribe at
  line 162 is returned into the promise chain rather than to React, so the auth
  listener is never cleaned up.
- The header "API healthy" pill (line 511) is hardcoded and never reflects real
  health.
- No dashboard path exists to revoke a device, or to edit, disable or delete a
  policy. Audit search, timeline and exports have no route and no UI —
  `export_csv`/`export_xlsx`/`export_pdf` are unreachable from the running
  service. The "Activity" view shows jobs only, never the audit log.
- Compliance evaluations are recomputed per request with a fresh `uuid4()` and
  never persisted, so `evaluation_id` is unstable and there is no history.
- Live-but-unused schema: `compliance_evaluations`, `compliance_results`,
  `remediation_attempts`, `notifications`, `event_outbox`, `packages`,
  `approved_folders`, `file_objects`, `file_operations`, `retention_policies`,
  `audit_exports`, `software_inventory`, `software_change_events`. No code reads
  or writes any of them.
- `audit_log.previous_hash`/`event_hash` are nullable with no constraint, so a
  future code path can insert unchained rows silently. Chain integrity is only
  verifiable by `AuditLog`, the in-memory test class; there is no production
  verification path. Chain ordering tie-breaks on a random UUID
  (`order by created_at desc, id desc`).
- `_job_from_row` rebuilds `JobRequest` with `confirmed=True` and re-runs the
  validators, so a row with a sensitive `action_type` and null `reason`, or a
  create-to-expiry span over 7 days, will 500 `GET /api/v1/jobs`.
- `GSWGuard.Agent.pdb` ships inside the release zip to every endpoint.
- `devices_member_read` exposes `credential_hash` to any org member including
  Viewer — not exploitable at 256-bit entropy, but unnecessary.
- Device endpoints declare `Header(alias="Authorization")` as required, so a
  missing header returns 422 rather than 401.
- Unhandled 500 responses skip `SecurityHeadersMiddleware` and CORS, because
  `BaseHTTPMiddleware` sits inside Starlette's `ServerErrorMiddleware`.
- Re-enrolling a machine hits `unique (organization_id, serial_number)` and
  returns `device_already_exists`; there is no re-enroll or device-replacement
  path.
- `docker-compose.yml` declares no healthchecks, though prior reports describe
  "healthy API/dashboard containers".
- No server-side bootstrap function exists, so the first organization and
  membership row must still be created by hand in SQL before anyone can sign in.

## Recommended order of work

1. C1 — bind the containers to loopback. One line, removes a live network
   exposure.
2. C2 — tighten the `devices` and `jobs` RLS policies to read-only for client
   roles.
3. H4 — split the compose env so the dashboard receives only its five public
   variables.
4. C4 — add HTTP-level authorization tests: one cross-organization negative and
   one insufficient-role negative per endpoint, plus device-credential
   rejection. Then execute the pgTAP suites.
5. H1 — reload the credential from the store inside the loop and stop nulling it
   on generic exceptions; wrap the initial `Load()`.
6. C3 — either implement the Windows security collectors or mark the Policies
   view as awaiting evidence.
7. H6 — drop the cascading FKs on the `audit_log` actor columns.
8. H2 — add a signed current-version pointer so updates can fire, then perform
   the Windows end-to-end install *and* update test that gate item 6 requires.
9. H3, H5, M1, M2, M3 — install-directory ACLs, connection pooling or a sync
   worker pool, per-route rate limits, offline threshold, snapshot retention.

## Acceptance rule (unchanged, restated)

A module is not complete because its Python classes or unit tests exist. It
needs an authenticated API path, persistence or an explicit test-only
designation, dashboard/receiver integration where applicable, automated tests
covering the authorization boundary, and a deployment smoke test. By that rule
the compliance, notification, package, file-operation, audit-search, export and
retention modules remain foundations, and the newly shipped Policies view is a
UI over an evaluation that cannot currently pass.
