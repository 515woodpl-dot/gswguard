# YorGuard implementation audit — 2026-07-28

## Scope

This audit compares the current repository and Raspberry Pi deployment with the master specification, execution amendment, and final clarifications addendum. It distinguishes validated implementation from unit-tested foundations and planned work.

## Validated and deployed

- Supabase JWT authentication with organization membership and owner/administrator/viewer roles.
- Persistent one-time enrollment tokens and hashed device credentials.
- Device enrollment, heartbeats, online/offline inventory, and cross-platform metadata for Windows, macOS, iOS, iPadOS, Android, and Linux.
- YorGuard dashboard sign-in, fleet metrics, device inventory, platform filtering, inventory refresh, and enrollment-token copy action.
- Windows receiver transport and DPAPI credential storage source; macOS receiver helper with Keychain storage.
- Docker Compose restart policies for the Raspberry Pi and healthy API/dashboard containers.
- Contract proof-of-concept, API tests, dashboard lint/typecheck/build, documentation validation, and the internal enrollment/heartbeat smoke test.

## Unit-tested foundations not yet productized

The following modules have tests and safety boundaries, but are not currently wired into authenticated HTTP routes, persistent service adapters, receiver payloads, or dashboard workflows:

- Full hardware/security/software inventory submission.
- PostgreSQL job submission, device polling, leases, completion, and result history.
- Compliance policy CRUD, evaluation history, score display, and remediation approval.
- Software-change notifications and delivery providers.
- Package catalog, Shared Drive provider, package approval UI, and agent-side deployment handlers.
- Approved-folder file operations over an authenticated remote protocol.
- Audit search, timeline, exports, retention execution, and dashboard views.

## Highest-priority debugging risks

1. `/health/ready` currently reports healthy without checking the configured database connection.
2. The API currently exposes only authentication, device listing, enrollment, and heartbeat routes; the other domain modules cannot yet be exercised through the deployed service.
3. The dashboard navigation labels for Activity and Policies are currently visual placeholders rather than routes.
4. The Windows agent has not been compiled in this macOS environment; GitHub Windows CI remains the authoritative build check.
5. Supabase SQL/pgTAP migrations and backup/restore have not been executed from this workspace.
6. Google Shared Drive delivery and package execution remain gated by their threat model and transport ADR.

## Recommended build order

1. Add a real readiness dependency check and an authenticated diagnostic endpoint.
2. Expose read-only device detail, audit search, and activity timeline APIs; add dashboard Activity/Devices views.
3. Add inventory submission and persistence, then show device health/security evidence.
4. Add job polling/result APIs only after inventory and device authorization are observable.
5. Add compliance evaluation and policy management.
6. Complete package/file operations only after the existing security gates are reviewed against real provider behavior.

## Acceptance rule

A module is not marked complete merely because its Python classes or unit tests exist. It must have an authenticated API path, persistence or an explicit test-only designation, dashboard/receiver integration where applicable, automated tests, and a deployment smoke test.
